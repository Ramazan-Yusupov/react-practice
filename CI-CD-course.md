# CI/CD для React-проекта

## 1. Что такое CI/CD

`CI/CD` — это подход к разработке, при котором проверки, сборка и доставка проекта автоматизируются.

### Что такое `CI`

`CI` (`Continuous Integration`) — это непрерывная интеграция.

Простыми словами:
- разработчик вносит изменения в код
- делает `push` в репозиторий
- система автоматически проверяет проект

Обычно в `CI` запускают:
- установку зависимостей
- линтер
- тесты
- сборку проекта

Цель `CI`:
- быстро находить ошибки
- не пропускать сломанный код в общую ветку
- проверять проект одинаково для всех участников команды

### Что такое `CD`

`CD` может означать 2 вещи:

1. `Continuous Delivery` — непрерывная доставка  
   Код автоматически подготавливается к релизу, но выкладку обычно подтверждает человек.

2. `Continuous Deployment` — непрерывное развертывание  
   Код после успешных проверок автоматически уходит в продакшн без ручного шага.

### Коротко

- `CI` = автоматически проверить проект
- `CD` = автоматически доставить или развернуть проект

## 2. Где используется CI/CD

`CI/CD` используют почти во всех современных проектах:

- в командной разработке
- в `GitHub` и `GitLab`
- при проверке `pull request`
- перед `merge` в `main`
- при автоматической сборке фронтенда
- при деплое на `Vercel`, `Netlify`, сервер или контейнер

### Пример из реальной работы

Ты делаешь изменения в компоненте, например в `Home` странице:

1. создаешь ветку
2. вносишь изменения
3. делаешь `push`
4. `GitHub Actions` автоматически запускает проверки
5. если `lint` и `build` прошли успешно, код можно безопаснее мержить

## 4. Как выглядит простой CI pipeline

Для текущего проекта минимальный pipeline будет таким:

1. разработчик делает `push`
2. `GitHub Actions` запускает workflow
3. проект скачивается на runner
4. устанавливаются зависимости
5. запускается `lint`
6. запускается `build`
7. если все прошло успешно, сборка считается зеленой

### Что это означает на практике

Если ты случайно:
- допустил ошибку в импорте
- сломал `TypeScript` типы
- оставил код, который не проходит `eslint`

то `CI` это покажет до того, как проблема попадет в основную ветку.

## 5. Почему для этого проекта подходит GitHub Actions

Для такого `React`-проекта логично начать именно с `GitHub Actions`, потому что:

- он хорошо подходит для учебных и реальных фронтенд-проектов
- не требует отдельного сервера
- хранит workflow прямо в репозитории
- легко запускается на `push` и `pull_request`
- хорошо подходит для `npm`, `Vite`, `TypeScript` и `eslint`

### Почему не стоит начинать со сложных инструментов

Можно использовать `Jenkins`, `GitLab CI`, `Docker`-сценарии и другие инструменты, но для текущего проекта это лишнее на старте.

Лучше сначала понять базовую идею:
- автоматическая проверка
- понятный workflow
- воспроизводимая сборка

## 6. Как обычно выглядит workflow файл

В `GitHub Actions` workflow хранится в папке:

```bash
.github/workflows/
```

Например:

```bash
.github/workflows/ci.yml
```

Основные части файла:

### `name`

Имя workflow, которое видно в `GitHub`.

Пример:

```yml
name: Frontend CI
```

### `on`

Показывает, когда запускать workflow.

Пример:

```yml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

Это значит:
- запускать при `push` в `main`
- запускать при `pull request` в `main`

### `jobs`

Описывает набор задач.

Пример:

```yml
jobs:
  build:
```

### `runs-on`

Показывает, на какой виртуальной машине будет выполняться job.

Пример:

```yml
runs-on: ubuntu-latest
```

### `steps`

Шаги, которые выполняются по очереди:

- получить код
- настроить `Node.js`
- установить зависимости
- запустить линтер
- собрать проект

## 7. Готовый минимальный CI пример для этого проекта

Ниже пример workflow, который подойдет текущему проекту.

```yml
name: Frontend CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-lint:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run linter
        run: npm run lint

      - name: Build project
        run: npm run build
```

## 8. Разбор workflow по шагам

### Шаг 1. `actions/checkout@v4`

```yml
- name: Checkout repository
  uses: actions/checkout@v4
```

Этот шаг скачивает код репозитория в runner.

Без него workflow просто не увидит файлы проекта.

### Шаг 2. `actions/setup-node@v4`

```yml
- name: Setup Node.js
  uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm
```

Этот шаг:
- устанавливает `Node.js`
- включает кэш зависимостей `npm`

Почему это полезно:
- сборка становится стабильнее
- версия `Node.js` фиксируется
- повторные запуски работают быстрее

### Шаг 3. `npm ci`

```yml
- name: Install dependencies
  run: npm ci
```

`npm ci` чаще используют в `CI`, а не `npm install`, потому что:

- установка идет строго по `package-lock.json`
- результат более предсказуемый
- команда быстрее для автоматической среды

### Шаг 4. `npm run lint`

```yml
- name: Run linter
  run: npm run lint
```

Этот шаг проверяет качество кода через `eslint`.

Для текущего проекта это особенно полезно, потому что помогает ловить:
- неиспользуемые переменные
- ошибки в хуках
- проблемы с код-стайлом и правилами `eslint`

### Шаг 5. `npm run build`

```yml
- name: Build project
  run: npm run build
```

В этом проекте команда сборки:

```bash
npm run build
```

выполняет:

```bash
tsc -b && vite build
```

То есть `CI` проверяет сразу 2 вещи:
- `TypeScript` не сломан
- приложение реально собирается через `Vite`

## 9. Почему в CI лучше использовать npm ci, а не npm install

### `npm install`

Подходит для локальной разработки.

Он:
- может обновить lock-файл
- работает гибче
- чаще используется вручную

### `npm ci`

Подходит именно для автоматических пайплайнов.

Он:
- ставит зависимости строго по lock-файлу
- не меняет `package-lock.json`
- работает предсказуемо

### Вывод

Для локальной работы:

```bash
npm install
```

Для `CI`:

```bash
npm ci
```

Можно настроить `GitHub` так, чтобы без успешного `CI` нельзя было мержить `pull request`.

## 12. Частые ошибки в CI/CD

### 1. Локально работает, а в CI падает

Частые причины:
- локально другая версия `Node.js`
- неактуальные зависимости
- разный регистр файлов
- локально есть файлы, которых нет в репозитории

### 2. Нет `package-lock.json`

Если `CI` использует:

```bash
npm ci
```

то нужен `package-lock.json`.

### 3. В `package.json` нет нужного скрипта

Например, workflow запускает:

```bash
npm run lint
```

а такого скрипта нет. Тогда pipeline упадет.

### 4. Неподходящая версия Node.js

Если проект использует одну версию `Node.js` локально, а в `CI` стоит другая, могут появиться неожиданные ошибки.

### 5. Ошибки регистра путей

На `Windows` файл может открываться даже при неаккуратном регистре, а в `Linux` runner в `GitHub Actions` может упасть.

Например:
- локально `Home.tsx`
- в импорте написано `home.tsx`

Для `CI` это уже может быть ошибкой.

## 13. Чем CI отличается от локальной проверки

Локальная проверка:
- запускается вручную
- зависит от твоей машины
- зависит от твоей среды

`CI`:
- запускается автоматически
- работает одинаково для всех
- помогает не забыть обязательные проверки

Идеальная практика:
- сначала запускать основные проверки локально
- потом полагаться на `CI` как на дополнительную защиту
